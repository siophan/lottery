# 子项目 D：客户端用户信息区（头像、昵称、积分余额） 设计

来源：第017章 第2节「用户端首页 / 用户信息区」、第3节普通账号「可修改本人头像和昵称」、第6节「头像与昵称」「随机默认值」「退出行为」、第7节账号列表「昵称」字段，验收 C-17-14、C-17-16（头像昵称部分）。依赖子项目 A（会话与拦截）、B（后台角色、账号列表）、C（积分余额与 10025）。
状态：已于 2026-10-07 与用户逐条确认（见第 8 节）。

## 1 范围

做：
- 客户端首页左上角用户信息区：头像 + 昵称，昵称下方显示当前积分余额；余额定时从后台读取。
- 用户修改本人头像（从本机选择图片）与昵称并保存；可恢复默认头像。
- 未设置时由后台按账号编号生成固定的随机默认昵称与默认头像。
- 管理后台：账号列表增加昵称；查看头像昵称；后台人员可重置为默认值（写审计）。

不做：
- 客户端原有「个人信息」「修改密码」等菜单（它们作用于共用的上游账号，属于另一个既有问题）。
- 昵称唯一性、敏感词过滤、头像人工审核流程。

## 2 数据

- `users` 新增 `nickname TEXT`、`avatar TEXT`，均可空；空表示使用默认值。由独立的迁移函数添加（不得放进会回填激活状态的 `_migrate_users`）。
- 默认值不落库，每次按账号编号确定性计算：同一账号永远得到同一默认值，不同账号尽量不同。
  - 默认昵称：「形容词 + 的 + 名词」，如「好运的海豚」；词表各约 30–50 个积极、中性的词，由账号编号的哈希选取。
  - 默认头像：5×5 左右对称的几何图案 SVG（类似 GitHub 默认头像），前景色色相由哈希决定、背景浅色；以 `data:image/svg+xml;base64,...` 返回。
- 实际显示值：`nickname` 非空用 `nickname`，否则默认昵称；`avatar` 非空用 `avatar`，否则默认头像。
- 昵称规则：去首尾空白后 1–12 个字符（按 Unicode 字符计），不含控制字符；不要求唯一。
- 自定义头像：
  - 客户端将图片居中裁为正方形并缩放到 128×128，编码为 JPEG 后上传 data URL。
  - 服务端只接受 `data:image/jpeg|png|webp;base64,` 前缀，base64 可解码、解码后不超过 100KB，且文件头魔数与声明类型一致；拒绝 SVG 及其他类型。
  - 原样以 data URL 文本存入 `users.avatar`。

## 3 客户端接口

均以请求头 `token`（会话令牌）认证，并经过 `gate.authorize` 的同一套拦截（10020/10022/10024/10025 等），与其他业务请求一致；接口需能从令牌取到当前用户。路由注册在 `/api/{path}` 兜底转发之前。

- `GET /api/user/profile` → `{"code":0,"data":{"code","nickname","avatar","points","nicknameIsDefault","avatarIsDefault"}}`（`nickname`/`avatar` 为实际显示值）。
- `GET /api/user/points` → `{"code":0,"data":{"points"}}`，供每 60 秒刷新，避免反复下载头像。
- `POST /api/user/profile`，请求体可含：
  - `nickname`：字符串，按规则校验；
  - `avatar`：data URL 字符串按规则校验，或 `null` 表示恢复默认头像。
  - 未出现的字段不改；成功返回与 `GET /api/user/profile` 相同的数据。
  - 校验失败返回 `{"code":1,"msg":...}`，文案：「昵称不能为空」「昵称最多 12 个字」「昵称包含不支持的字符」「头像格式不支持」「头像图片过大」。
- 用户修改头像昵称不写审计。

## 4 客户端界面

- 位置：首页顶部左上角原空白处（窗口宽约 260px，顶部区高 120px）。放在半透明 `.card` 之外、绝对定位、层级高于背景，设置 `-webkit-app-region: no-drag` 以便点击。
- 布局：头像 44px 圆形，高度约等于右侧两行；右侧第一行昵称（白色 14px，过长省略），第二行「积分：N」（白色 12px）。
- 数据刷新：
  - 进入首页先用登录返回的余额立即显示（登录补丁把 `res.data.points` 存入 `localStorage`），再请求 `GET /api/user/profile` 补全头像昵称。
  - 之后每 60 秒请求 `GET /api/user/points`；首页重新激活时也刷新一次。
  - 网络失败或非 0 且非拦截码时保留上次显示，不弹提示。
  - 拦截码（含 10025）由现有请求拦截器统一处理：提示文案并退回登录页；退出入口不受影响。
- 编辑弹窗（点击信息区打开，适配 260px 宽）：
  - 大头像预览，下方「更换头像」「恢复默认」；昵称输入框（最多 12 字）；「保存」「取消」。
  - 「更换头像」用 `<input type="file" accept="image/*">` 打开系统选择窗口；选中后在本机裁剪压缩并预览，非图片或无法解码提示「请选择图片文件」。
  - 只有点「保存」才提交；成功后关闭弹窗并立即更新左上角；失败在弹窗内显示服务端文案。
- 实现：
  - 独立的纯 DOM 脚本 `client/user-profile.js`（UMD，暴露 `window.dsProfile`，可在 Node 下用假 DOM 测试），由 `client/index.html` 的 `<script>` 引入，沿用 `account-onboard.js` 的做法。
  - `scripts/patch-ds-client.js` 新增补丁层（独立标记，幂等）：首页模板加入挂载点；首页显示时调用 `dsProfile.mount(el, { request, points })`，`request` 为首页现有的 axios 请求实例，令牌注入与拦截自动生效；登录补丁保存登录返回的余额。
  - 打包已包含 `client/**`，Mac 与 Windows 共用，不使用平台专有接口。

## 5 管理后台

- `/admin/users` 每行增加 `nickname`（实际显示值）；前端账号列表增加「昵称」列，可按昵称筛选；代理视角同样显示。列表不返回头像。
- `GET /admin/users/{code}/profile` → 昵称、头像（实际显示值）及是否默认；代理只能查看本人名下账号。
- `POST /admin/users/{code}/profile/reset`：把 `nickname`、`avatar` 置空恢复默认；仅最高权限者与管理员；写审计 `user.profile_reset`（目标为账号编号，详情记录重置前是否为自定义值）。
- 账号操作增加「头像昵称」：弹窗显示头像与昵称；后台人员可见「重置为默认」，二次确认后执行。

## 6 测试

  - 三个客户端接口的认证与拦截（无令牌、封禁、余额 0 → 10025）；路由优先于兜底转发；

- 客户端（node --test）：
  - 补丁层：标记存在、重复执行无变化、各模块源码可解析、锚点不匹配时报错；登录保存余额；首页挂载调用；
  - `user-profile.js`：渲染、余额刷新与失败保留、编辑保存成功/失败、恢复默认、图片裁剪压缩参数。
- 后台前端：`tsc --noEmit` 与打包通过。

## 7 上线

- 迁移只新增可空列，无需数据处理；后端可先于客户端部署（旧客户端不调用新接口）。
- 新客户端与子项目 C 所需的新客户端合并为一次发版。

## 8 已确认决定（2026-10-07）

- 默认值样式：词组昵称 + 几何图案头像，由账号编号固定生成。
- 后台管控：账号列表显示昵称，可查看头像；最高权限者与管理员可一键重置为默认，写审计。
- 方案：头像昵称与默认值均由后台负责（存储与生成），客户端只显示与上传。
- 余额每 60 秒刷新；余额为 0 按现有 10025 规则提示并退回登录页。
- 客户端原有「个人信息」「修改密码」不在本期范围。
